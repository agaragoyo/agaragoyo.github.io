# 아가라고요

아가라고요는 웹프로그래밍 개론 팀 프로젝트입니다. 2000년대에 유행하던 개인 홈페이지를 "진짜 집 꾸미기"로 바꿔 보자는 생각에서 시작했습니다.
사이트 전체가 옛날 컴퓨터 한 대처럼 생겼습니다. 전원 버튼을 누르면 부팅과 로그인을 거쳐 바탕화면이 뜹니다.
방 꾸미기와 미니게임은 이 컴퓨터에 깔린 앱입니다. 꾸민 방은 링크로 친구에게 보여 줄 수 있습니다.

지금 배포된 모습은 https://agaragoyo.github.io/ 에 있습니다.
화면은 2005년 무렵의 은색 평면 브라운관 모니터와 그 시절 운영체제의 모양새로 보여 줍니다.
1998, 2005, 2010 세 시대를 만들어 비교해 본 뒤, 11주차 알파 테스트를 마치고 2005로 정했습니다.

사이트가 어떻게 동작하는지, 왜 이렇게 만들었는지는 [docs/guide.md](docs/guide.md)에 정리되어 있습니다.
어떤 파일이 어디에 있고 무슨 일을 하는지는 [docs/file-map.md](docs/file-map.md)에서 찾으면 됩니다.

## 내 컴퓨터에서 열어 보기

이 사이트는 npm이나 빌드 도구 없이 HTML, CSS, JS 파일만으로 동작합니다.
다만 `index.html`을 더블클릭해서 열면 빈 화면만 나옵니다. 파일로 연 페이지에서는 브라우저가 JS 모듈을 막기 때문입니다.
그래서 작은 로컬 서버를 띄워서 엽니다. 파이썬만 설치되어 있으면 됩니다.

```bash
python tools/serve.py
```

서버를 띄운 뒤 브라우저에서 http://localhost:8123 을 엽니다. 파일을 고치고 새로고침하면 바로 반영됩니다.
`python -m http.server`로 띄우면 브라우저가 예전 JS를 계속 쓰기 때문에 고친 내용이 반영되지 않을 때가 있습니다.
반드시 `tools/serve.py`로 띄워 주시기 바랍니다.

## 작업을 올리는 방법

main 브랜치의 파일이 곧 배포되는 사이트입니다. 그래서 main은 누구도 직접 고치지 않습니다.
고칠 것이 있으면 main에서 작업용 갈래인 브랜치를 따로 만들어 그곳에서 작업합니다.
작업이 끝나면 Pull Request(PR)를 엽니다. PR은 브랜치에서 고친 내용을 main에 합쳐 달라는 요청서입니다.
PR 페이지에는 바뀐 내용이 줄 단위로 표시되고 자동 점검도 그 페이지에서 실행됩니다.

PR은 Admin이나 Maintain 권한을 가진 관리자가 확인한 뒤 합칩니다.
자기 PR의 합치기 버튼이 활성화되어 있더라도 직접 합치지 말고 관리자의 확인을 기다려 주시기 바랍니다.
PR이 합쳐지면 1~2분 뒤 사이트에 자동으로 반영됩니다.

무엇을 올리는지에 따라 방법이 다릅니다. 코드를 고칠 때는 프로그램을 설치하고 내 컴퓨터에서 확인해야 합니다.
그림 파일만 넣거나 사이트를 써 보고 의견을 낼 때는 아무것도 설치하지 않고 GitHub 웹 페이지에서 끝납니다.
게임을 만들면서 그 게임에 쓸 그림도 넣는다면 코드를 고칠 때의 방법으로 한 번에 올리면 됩니다.

### 코드를 고칠 때

미니게임이나 기능, 화면 모양처럼 코드를 고칠 때는 레포를 내 컴퓨터로 받아서 작업합니다.
git 명령어가 낯설다면 [GitHub Desktop](https://desktop.github.com/)을 써도 됩니다. 로컬 서버를 띄우려면 파이썬도 필요합니다.

1. 레포를 내 컴퓨터로 받습니다(GitHub Desktop의 Clone repository).
2. 작업을 시작하기 전에 main을 최신으로 받고(Fetch origin, Pull) 새 브랜치를 만듭니다.
   브랜치 이름은 `GitHub아이디/주제` 형식이며 영어 소문자와 하이픈만 씁니다(예: `<아이디>/sand-dig`).
3. 파일을 고친 뒤 로컬 서버에서 직접 열어 확인합니다.
   `python tools/check.py`로 자동 점검을 돌려 오류가 없으면 커밋합니다. 커밋 메시지에는 무엇을 왜 바꿨는지 한국어로 한 줄 적습니다.
4. Push origin으로 올린 다음 Create Pull Request를 누릅니다. PR 설명 칸에 나오는 질문에 답을 채웁니다.
   PR 화면 아래에 자동 점검(Check) 결과가 표시됩니다. 빨간 X가 뜨면 눌러서 무엇이 틀렸는지 확인하고 고칩니다.
5. 수정 요청을 받으면 같은 브랜치에서 고친 뒤 다시 Push합니다. 새 커밋은 같은 PR에 이어서 붙습니다.

여러 사람이 같은 파일을 동시에 고치면 합칠 때 충돌이 납니다. 미니게임처럼 내 폴더 안에서 끝나는 작업은 충돌이 거의 없습니다.
내 작업과 관계없는 파일의 들여쓰기나 줄바꿈은 건드리지 않습니다.
`style.css`나 `src/` 아래 파일처럼 모두가 쓰는 파일을 크게 바꿀 때는 팀에 미리 알려 주시기 바랍니다.
`tools/stamp.py`는 배포할 때 GitHub Actions가 실행하므로 직접 돌리지 않습니다.

### 그림 파일만 넣을 때

가구 그림처럼 그림 파일만 넣을 때는 GitHub 웹 페이지에서 바로 올립니다. 따로 설치할 것은 없습니다.

1. 레포 페이지에서 파일이 들어갈 폴더로 들어갑니다. 가구 그림은 `assets/furniture` 폴더입니다.
2. 오른쪽 위의 **Add file**에서 **Upload files**를 고르고 파일을 화면에 끌어다 놓습니다.
3. 아래 칸에 무엇을 올렸는지 한 줄 적고 **Propose changes**를 누릅니다. main이 보호되어 있어서 GitHub이 새 브랜치를 자동으로 만들어 줍니다.
4. 다음 화면에서 **Create pull request**를 누르면 끝납니다. 웹으로 올린 PR도 같은 자동 점검을 거칩니다.

파일 이름이 틀리면 사이트가 그림을 찾지 못하므로 이름 규칙을 꼭 지켜 주시기 바랍니다.
가구 그림은 `가구id.png`, 돌려 놓은 모습은 `가구id-r.png`입니다. 돌린 그림이 없으면 원래 그림을 좌우로 뒤집어 씁니다.
가구 id는 `data/furniture.js`에 적힌 영어 이름입니다(예: `desk`). 그림을 그릴 때 맞출 것(바닥 기울기, 칸 채우기, 벽 가구는 정면)은
`docs/checklists.md`의 "소리나 그림을 넣었다면"에 있고, 칸에 맞지 않는 그림은 자동 점검이 경고로 알려 줍니다.

### 써 보고 의견을 낼 때

https://agaragoyo.github.io/ 에서 직접 써 보고 버그나 아이디어가 있으면 레포 위쪽의 **Issues** 탭에 남겨 주시기 바랍니다.
**New issue**를 누르면 "버그 제보"와 "아이디어" 양식이 나옵니다.

## 새 기능을 붙이는 곳

만들려는 것마다 시작하는 자리가 정해져 있습니다. 모두 같은 자리에서 같은 방식으로 붙여야 서로 부딪히지 않습니다.

- 미니게임이나 새 앱은 `apps/_template` 폴더를 복사해서 시작하고 `data/apps.js`에 한 줄을 넣습니다. 자세한 방법은 `apps/README.md`에 있습니다.
- 바탕화면에서 가구를 두 번 눌렀을 때 열리는 화면(가구 기믹)도 앱으로 만듭니다.
  `data/apps.js`의 그 앱 줄에 `folder: 'furniture'`를 붙이고 `data/furniture.js`의 그 가구에 `gimmick: 'app:<앱 id>'`를 넣습니다.
- 다른 사이트에 있는 남의 게임은 파일을 옮겨 오지 않고 주소로 이어 줍니다. 창 안에 띄울 수 있으면 `src`에, 창 안에서 돌지 않으면 `href`에 주소를 넣습니다. `href`는 새 탭으로 열립니다.
- 새 가구는 `data/furniture.js`에 한 줄을 넣고 그림을 `assets/furniture/<가구 id>.png`로 올립니다.
- 방 안을 걷는 아바타는 `src/avatar.js`가 맡습니다. 아바타 그림은 `data/avatars.js`에 한 줄을 넣고 `assets/avatars/<아바타 id>.png`로 올리며, 그림 규격은 `data/avatars.js` 맨 위에 있습니다.
- 방이나 놀이터 같은 새 공간은 `src/config.js`의 `SCENES`에 한 줄을 넣고 가구의 `scene`에 그 id를 적습니다. 바깥 공간이면 내 방으로 돌아오는 울타리 문 자리도 `gate`로 정합니다.
- 모니터와 화면 모양은 `index.html`과 `style.css`가 맡습니다. `style.css`는 절마다 제목 주석이 있고, 절의 순서는 `docs/file-map.md` 맨 아래에 있습니다.
- 부팅, 창, 방 꾸미기, 배경음악처럼 컴퓨터 자체의 동작은 `src/` 폴더에 있습니다.

이 밖의 자리와 파일마다 맡은 일은 [docs/file-map.md](docs/file-map.md)에 정리되어 있습니다.

## 지켜야 할 것

npm과 빌드 도구, 프레임워크는 쓰지 않습니다. 브라우저에서 그대로 열리는 HTML, CSS, JS만 쓰고 라이브러리가 필요하면 CDN 주소로 불러옵니다.
사이트는 PC와 마우스를 기준으로 만듭니다.
실제 윈도우의 로고나 이름, 다른 회사의 로고 색은 쓰지 않습니다. 그 시절의 분위기만 따릅니다.
미니게임은 남의 게임을 그대로 베끼지 않고 같은 장르의 우리 게임으로 만듭니다.
추억의 플래시 게임처럼 남의 게임을 넣을 때는 파일을 옮겨 오지 않고 원작 주소로 이어 줍니다.
누르면 새 탭이 열리거나 무언가 지워지는 기능은 누르기 전에 그 결과를 알 수 있게 만들고, 확인 창의 단추는 "예/아니오" 대신 "새 탭에서 열기"처럼 결과를 말하는 이름으로 씁니다.
앱을 만들 때 지킬 것은 `apps/README.md`의 "지킬 것"에 따로 정리되어 있습니다.

## AI와 같이 작업할 때

Claude Code, Codex, Cursor 같은 AI 코딩 도구는 레포의 `AGENTS.md`를 스스로 읽고 우리 규칙을 따릅니다.
ChatGPT나 Claude 웹 같은 채팅에 코드를 맡길 때는 `AGENTS.md` 내용을 먼저 붙여 넣고 시작하시기 바랍니다.
AI가 만든 코드도 로컬 서버에서 직접 눌러 보고 나서 올립니다.

무엇을 만들지는 `docs/requirements.md`, 누가 무엇을 맡았는지는 `docs/tasks.md`, 올리기 전에 확인할 것은 `docs/checklists.md`에 정리되어 있습니다.
AI에게 일을 맡길 때도 이 세 문서를 함께 읽게 하면 팀이 정한 방향에서 벗어나지 않습니다.

## 기록 남기기

작업 한 덩어리를 마치면 `worklog/` 폴더에 작업 일지를 한 편 써서 같은 PR에 넣습니다. 형식은 `worklog/README.md`에 있습니다.
나중에 그 코드를 고칠 사람에게 왜 그렇게 만들었는지 알려 주는 기록이므로 몇 줄이면 충분합니다.
같은 실수가 반복될 만한 함정을 찾았다면 `known-issues.md`에도 항목을 하나 추가합니다. 코드를 고치기 전에 이 파일을 한 번 읽어 두면 같은 함정에 빠지지 않습니다.

파일을 새로 만들거나 옮기거나 지웠다면 `docs/file-map.md`도 같은 PR에서 고칩니다. 빠뜨린 파일은 자동 점검이 알려 줍니다.
사이트의 동작이 바뀌었다면 `docs/guide.md`의 해당 절도 함께 고칩니다.
무엇을 만들지 새로 정했다면 `docs/requirements.md`를, 할 일이 생기거나 끝났다면 `docs/tasks.md`를 고칩니다.

이 레포는 누구나 볼 수 있는 공개 레포입니다. 일지와 커밋 메시지, PR 설명, Issues에는 공개해도 되는 작업 내용만 적습니다.
팀원 이름과 팀 안의 이야기는 적지 않습니다. 비밀번호나 API 키 같은 값도 파일에 넣지 않습니다.
