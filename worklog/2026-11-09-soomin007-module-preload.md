# 2026-11-09 모듈 미리 받기 (soomin007)

## 한 일
느린 연결에서 첫 화면이 뜨기까지 기다리는 시간을 줄였다. `main.js`는 import로 이어진 모듈 29개를 여섯 단계에 걸쳐 다 받은 뒤에야 돌았다.
브라우저는 파일 하나를 받아 읽어야 그다음에 받을 파일을 알기 때문이다. 이제는 배포할 때 `tools/stamp.py`가 받을 모듈 목록을 `index.html`에 적어 두고,
크롬 계열 브라우저는 HTML을 읽자마자 모듈을 한꺼번에 받는다. 사파리는 WebKit 버그 때문에 예전처럼 차례로 받는다.
재는 동안 찾은 개발 서버의 연결 거부도 같이 고쳤다.

## 바꾼 파일
- `tools/stamp.py`: `src/main.js`에서 정적 import를 따라 닿는 모듈마다 import map과 같은 `?v=` 주소로 `<link rel="modulepreload">` 줄을 만들어 `<template id="modulepreload">`에 채운다. 채울 자리나 순서가 틀리면 멈추고 알린다
- `index.html`: import map 다음에 template과, 크롬 계열에서만 그 줄을 꺼내 붙이는 인라인 스크립트. import map과 함께 스타일시트 링크보다 앞으로 옮겼다
- `src/main.js`: `CHROMIUM` 위에 `index.html`의 같은 판별식을 가리키는 주석
- `tools/check.py`: `check_stamp`. PR마다 stamp.py를 미리 돌려 배포할 때 실패할 자리를 알린다
- `tools/serve.py`: 연결 대기열을 5칸에서 64칸으로 늘렸다
- `known-issues.md`(15번에 보탬, 43번, 44번), `docs/file-map.md`, `docs/guide.md`, `docs/tasks.md`

## 정한 것과 이유
- 크롬에서 DevTools의 Fast 3G와 비슷한 연결(왕복 560ms, 초당 180KB)로 고치기 전과 후를 다섯 번씩 번갈아 재고 가운데 값을 썼다.
  깃허브 페이지는 HTTP/2와 gzip으로 내보내므로 같은 방식으로 내보내는 시험 서버에서 쟀고, 고치기 전 값은 실제 배포 주소와 거의 같았다(main.js 4.06초와 4.12초).

  | 크롬, Fast 3G 정도 | 고치기 전 | 고친 뒤 |
  | --- | --- | --- |
  | 모듈 요청이 나간 묶음 | 6 | 1 |
  | main.js가 돎(`--u`가 정해짐) | 4.05초 | 1.96초 |
  | 가림막이 걷히기 시작 | 6.18초 | 4.97초 |
  | 가림막이 빠짐 | 6.59초 | 5.37초 |

- 고친 뒤에는 가림막이 글꼴을 기다리는 3초 상한(known-issues 42)에 걸려 걷힌다. 그때 갈무리 보통 굵기(505KB)는 아직 받는 중이라
  1.3초쯤 기본 글꼴로 보이다가 6.2초에 갈무리로 바뀐다. 고치기 전에는 글꼴이 먼저 와서 상한에 걸리지 않았다.
- 로컬 `serve.py`(HTTP/1.0, 압축 없음)에서는 main.js가 5.65초에서 4.54초로 당겨졌지만 가림막은 7.1~7.4초로 비슷했다.
  압축하지 않은 모듈 205KB가 글꼴과 대역폭을 나눠 쓰고, 가림막은 글꼴을 기다리기 때문이다.
  연결 제한이 없으면 배포 사이트는 main.js 0.32초, 가림막 빠짐 0.98초였다. 이때는 모듈 단계 하나가 40~80ms라 줄어드는 시간도 0.2초 안팎이다.
- 미리 받는 주소는 import map이 바꿔 준 주소와 글자까지 같아야 브라우저가 같은 모듈로 친다. 그래서 stamp.py가 import map을 만드는 자리에서 같은 값으로 채우고,
  29개를 한 번씩만 받는 것을 확인했다. `import()`로 나중에 부르는 모듈은 필요할 때 받으려고 나눈 것이므로 따라가지 않는다.
- 처음에는 모든 브라우저에 `<link>`를 바로 적었다. 그런데 WebKit에서는 미리 받던 모듈이 한 번 실패한 탭이 새로 고침해도 그 모듈을 다시 요청하지 않아
  가림막에 갇혔다(WebKit 버그 270357, known-issues 43). 모듈을 받지 못했을 때 사용자가 할 수 있는 일은 가림막의 새로 고침 단추뿐이다.
  그래서 볼록 화면(known-issues 30)처럼 확인하지 못한 엔진에서는 끄고 크롬 계열에서만 켰다. 크롬 계열에만 붙여도 크롬에서 빨라지는 정도는 같았다.
- template과 인라인 스크립트는 스타일시트 링크 앞에 두었다. 스타일시트 뒤의 인라인 스크립트는 jsdelivr의 갈무리 CSS까지 다 받을 때까지 기다리기 때문이다.
  import map보다 앞이면 브라우저가 import map을 무시할 수 있어서 그 뒤에 두었다.
- 원래 `serve.py`로 평소처럼 열어도 15번 중 1번은 `sound.js`가 연결 거부로 실패해 가림막이 남았다. 대기열을 64칸으로 늘리니
  연결 30개, 60개를 한꺼번에 열어도, 15번 다시 열어도 실패가 없었다(known-issues 44).

## 남은 일과 알아 둘 것
- 확인한 것: 크롬은 미리 받을 줄 29개가 붙어 모듈을 한 번에 받고 오류가 없다. WebKit은 줄이 붙지 않고 여섯 단계로 받으며,
  모듈 하나를 막은 뒤 새로 고침하면 3번 모두 되살아났다. 레포 밖 가림막 점검은 크롬 29/29, WebKit은 고치기 전과 같은 23/29다
  (이 PC의 WebKit은 원래 1.4초쯤 걸려 "1초 안에 걷힘"과 "점" 항목이 실패한다). 파이어폭스는 확인하지 못해 지금처럼 차례로 받는다.
- 사파리에 270357을 고친 버전이 나오면 확인하고 모든 브라우저로 넓힌다(`docs/tasks.md`의 알려진 문제).
- 합쳐서 배포한 뒤 같은 방법으로 배포 주소를 다시 재서 위 숫자와 맞춰 본다.
- 느린 연결에서 첫 화면의 남은 짐은 갈무리 글꼴 672KB(보통 505KB, 굵게 167KB)다. 더 줄이려면 글꼴 쪽을 봐야 한다.
- 재는 데 쓴 스크립트는 레포 밖 `%LOCALAPPDATA%\agarago-webkit-check\scripts`에 있다. 위 표는 `load-timing.mjs`와 HTTP/2 시험 서버 `h2-serve.mjs`로,
  시간별 사진은 `load-frames.mjs`로, 가림막 점검은 `loader-check.mjs`로 했다.
  `loader-check.mjs`가 style.css가 오기 전의 모양을 읽어 점이 보였다고 잘못 세던 것을 고쳤다. WebKit으로 돌릴 때는 node를 띄우기 전에 `PLAYWRIGHT_BROWSERS_PATH`를 정한다.
- stamp.py를 돌린 `index.html`은 커밋하지 않는다(known-issues 15). 시험할 때는 복사본에서 돌린다.
