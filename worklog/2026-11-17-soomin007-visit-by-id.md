# 2026-11-17 아이디로 친구 방 찾아가기 (soomin007)

## 한 일
이름이나 아이디로 친구 방을 찾아가자는 아이디어가 팀에서 나와, 링크를 만든 사람이 방에 아이디를 정하고
친구가 이웃집 목록 창 아래 칸에 그 아이디를 쳐서 찾아오게 했다(F31).
처음에는 짧은 링크의 방 번호 여덟 글자를 치는 칸을 만들려 했다. 번호는 친구가 먼저 건네야 해서 링크를 보내는 것과 다르지 않았고,
대문자와 소문자가 섞여 말로 불러 주기도 어려워서 접었다.

## 바꾼 파일
- `firestore.rules`: `handles/{아이디}` 문서. 누구나 한 문서씩 읽되 목록 읽기는 막는다. 만들기는 자기가 올린 방으로만 하고,
  이미 있는 아이디는 고치지 못하며, 지우기는 정한 사람만 한다
- `src/cloud.js`: "아이디" 절(`normalHandle`, `handleFrom`, `findHandle`, `claimHandle`, `dropHandle`, `myHandle`, `HANDLE_RE`).
  링크를 지우면(`unshare`) 아이디를 먼저 지우고, 익명 계정이 지워졌거나 방을 고칠 수 없게 되면 아이디도 잊는다
- `src/apps/share-app.js`: 링크가 있으면 아이디 칸과 "아이디 정하기", 정한 뒤에는 읽기 전용 칸과 "아이디 지우기"(한 번 더 묻는다).
  링크 지우기의 확인 글에 아이디도 지운다고 적었고, 창 높이를 410에서 530으로 늘렸다
- `src/neighbors.js`: 목록 창 아래의 친구 아이디 칸(`handleForm`)과 오류 네 가지. 창 높이에 칸 높이(`FORM_H`)를 더했다
- `src/os.js`: `os.visit`이 들어가기 전에 그 방의 가구 그림을 받기 시작한다. 아이디로 찾은 방은 부팅할 때 받아 두지 않았기 때문이다(known-issues 54)
- `src/login.js`: 이 컴퓨터 초기화의 확인 글에 아이디를 더했다
- `style.css`: `.handle-form`, `.handle-msg`, `.share-error`
- `tools/check.py`: `check_cloud`가 `HANDLES` 컬렉션과 `HANDLE_RE`가 규칙의 `handle.matches`와 같은지 본다
- `tools/smoke.mjs`: 가짜 서버(`fakeCloud`)가 아이디 문서에 답한다. 공유하기의 아이디 정하기와 지우기, "아이디로 찾아가기" 절을 더했다
- `tools/night-contrast.mjs`: 이웃집 목록 창의 아이디 칸을 빈 채로 보내 오류 글자의 밤 대비도 잰다
- 문서: `docs/requirements.md`(F31과 정한 것), `docs/guide.md`, `docs/file-map.md`, `docs/tasks.md`

## 정한 것과 이유
- 화면에 보이는 닉네임과 찾을 때 쓰는 아이디를 나눴다. 닉네임은 겹쳐도 되지만 아이디는 먼저 정한 한 사람만 쓴다
  (인스타그램의 사용자 이름, 2023년에 바뀐 디스코드의 사용자명). 닉네임으로 바로 찾으면 같은 이름을 고른 사람끼리 섞인다.
- 아이디를 정한 사람만 찾히고 정확히 친 아이디만 열린다. 목록이나 비슷한 이름 찾기를 두면 링크를 한 사람에게만 보낸 사람까지 드러난다.
  동물의 숲 꿈 번지도 섬을 올린 사람만 번호를 받는다.
- 아이디는 한글 완성 글자, 영문 소문자, 숫자로 2~12자다. 말로 불러 주기 쉽게 영문 대문자는 소문자로 바꾸고 띄어쓰기와 맨 앞의 @는 뺀다(`normalHandle`).
  길이는 닉네임과 같은 12자로 했다.
- 아이디 칸에는 닉네임에서 쓸 수 있는 글자를 미리 넣는다. 대부분은 단추만 누르면 이름이 그대로 아이디가 된다.
- 방 하나에 아이디는 하나다. 새로 정하면 새 아이디를 만든 뒤 예전 것을 지운다. 먼저 지우면 새 아이디를 못 정했을 때 둘 다 잃는다.
- 아이디는 있는데 방이 없거나 깨졌으면 손님에게 없는 아이디와 같은 글을 띄운다. 손님에게는 어느 쪽이든 갈 곳이 없다.
- 오류는 칸 바로 아래에 띄우고 친 글자는 남긴다. 이웃집 창은 폭이 좁아서 오류의 두 문장을 한 줄씩 쓰고,
  두 줄 자리를 늘 잡아 두어 오류가 떠도 창이 스크롤되지 않게 했다(known-issues 73).

## 확인한 것
- 눌러 보기 점검에 공유하기의 아이디 정하기와 지우기, 링크를 지우면 아이디도 지워지는지, 이웃집 창의 오류 다섯 가지와 들어가기,
  아이디로 온 손님의 코르크 보드가 그 방 번호로 쪽지를 찾는지를 넣었다. 두 창 모두 오류가 떠도 스크롤되지 않는지 잰다.
- 아이디로 찾은 뒤에야 문 소리를 튼다(서버를 기다린 뒤). `docs/checklists.md`의 "누른 뒤 기다렸다 부르는 소리"에 들어서,
  WebKit 27.2(Playwright, 윈도우 빌드)에서 0.8초를 기다린 뒤에도 소리가 막히지 않고 그 방에 들어가는 것을 봤다. 파이어폭스는 이 PC에 받아 두지 않아 보지 못했다.
- 규칙을 콘솔에 게시한 뒤 익명 계정 둘로 진짜 서버에 REST를 불러 36가지를 시험했다. 영문, 한글, 한글 12자 아이디는 만들어지고(정규식의 `가-힣`과 `{2,12}`는 글자로 센다),
  목록 읽기, 남의 방으로 만들기, uid가 다른 문서, 없는 방, 칸이 더 있는 문서, 꼴이 틀린 아이디 일곱 가지, 남의 아이디 지우기는 막혔다.
  남이 먼저 정한 아이디를 `exists: false`로 만들면 규칙보다 먼저 409 ALREADY_EXISTS가 오고, 조건 없이 덮어쓰면 403이다. 사이트는 둘 다 다시 읽어 "이미 사용 중"으로 알린다.
- 처음 게시한 뒤에는 서버가 2분 넘게 옛 규칙으로 답했고, 같은 파일을 다시 게시하자 바로 들어갔다. 게시한 뒤에는 없는 아이디 읽기가 404인지부터 본다(known-issues 59에 덧붙임).

## 남은 일과 알아 둘 것
- 규칙은 2026-11-17에 콘솔에 게시했다. `firestore.rules`의 `handles` 부분을 고치면 다시 게시해야 한다(known-issues 59).
- 규칙은 같은 아이디를 둘이 쓰는 것만 막고, 한 사람이 아이디를 여러 개 만드는 것은 막지 않는다. 사이트는 방 하나에 하나만 두지만 REST를 직접 부르면 여럿을 만들 수 있다.
- 저장소를 지운 브라우저나 지워진 익명 계정의 아이디는 서버에 남아 다른 사람이 쓰지 못한다. 그 계정의 방이 고칠 수 없게 남는 것과 같은 한계다.
- 로그인 화면에는 아이디 칸이 없다. 처음 온 사람은 사용자를 만든 뒤 현관문으로 목록 창을 연다(튜토리얼 셋째 단계가 그 창을 연다).

## 이어서: 로그인 화면에서도 아이디로 찾아가기

처음 온 사람은 사용자를 만들고 튜토리얼 셋째 단계나 방의 현관문까지 가야 아이디 칸을 봐서, 최종 발표에서 아이디만 듣고 바로 놀러 오기에는 단계가 많았다.
로그인 화면에 칸을 두기로 하고, 자리 세 가지(왼쪽 안내 아래에 늘 펼친 칸, 같은 자리의 글자 단추, 아래 띠 오른쪽)를 실제 화면에 끼워 찍어 견줬다.
처음 생각한 사용자 목록 아래는 들어가지 않았다. 처음 온 사람의 화면에서 목록(이웃집 여섯 집과 새 사용자 만들기)이 가운데 띠 660px 가운데 646px을 채우고 있었다.
견준 끝에 새 사용자 만들기를 왼쪽 단으로 옮기고 친구 아이디 칸을 이웃집 아래에 두는 배치로 정했다.
이웃집은 팀원의 방을 미리 넣어 둔 친구 집이라, 이렇게 하면 친구에게 가는 길이 오른쪽 단 하나에 모인다.

- `src/neighbors.js`: 아이디로 방을 찾는 칸과 단추, 오류 글을 `handleInput`으로 뽑았다. 이웃집 목록 창의 `handleForm`은 오류를 보이는 모양과 들어가는 길만 정한다
- `src/login.js`: 왼쪽 단(`.users-own`)에 내 사용자와 초기화나 새 사용자 만들기, 오른쪽 단(`.users-friends`)에 친구 집. 이웃집 아래의 친구 아이디 칸은 `handleTile`이다.
  닉네임 칸의 키보드 소리를 `keySound`로 뽑아 두 칸이 같이 쓴다
- `index.html`, `style.css`: 두 단의 상자와 `.user.by-handle`. 안내 글 규칙을 `.login-left > p`로 좁혔다(known-issues 24에 한 줄)
- `tools/smoke.mjs`: 로그인 화면의 칸을 찾는 선택자를 두 단에 맞춰 좁히고(known-issues 72에 한 줄), "로그인 화면의 친구 아이디 칸" 절을 더했다
- `tools/night-contrast.mjs`: 사용자를 만들기 전에 로그인 화면을 친구 아이디 칸의 오류 풍선을 띄운 채 한 번 잰다
- 문서: `docs/requirements.md`(F31과 정한 것), `docs/guide.md`, `docs/file-map.md`, `docs/tasks.md`

내 사용자도 왼쪽으로 옮겼다. 내 집이 있는 사람의 화면에서 내 사용자를 오른쪽에 두고 아이디 칸까지 더하면 706px이 되어 가운데 띠를 넘는다.
그래서 왼쪽은 나, 오른쪽은 친구 집으로 나눴다. 친구 링크로 들어왔을 때는 이웃집처럼 아이디 칸도 뺐다. 링크가 이미 갈 곳을 알려 주므로 그 친구 집 하나에 눈이 가게 둔다.

찾은 방에는 짧은 링크로 온 친구 집과 같은 길(`enter('visit', 집, 실행 번호, 방 번호)`)로 들어간다. 방 번호가 boardId라서 손님이 그 방의 코르크 보드에 쪽지를 남긴다.
아이디로 찾은 방은 부팅할 때 받아 두지 않았으므로 들어가기 전에 가구 그림을 받기 시작한다(known-issues 54).
로그인 화면의 다른 사용자 칸처럼 문 소리는 내지 않는다. 그래서 서버를 기다린 뒤에 소리를 부르는 일도 없다.

오류는 이웃집 창처럼 칸 아래 글자로 쓰지 않고, 닉네임 칸처럼 칸을 빨갛게 두르고 노란 풍선으로 띄웠다. 파란 바탕에서는 빨간 글자가 잘 읽히지 않고,
윈도우 XP도 로그인 화면에서 암호가 틀리면 칸 아래에 풍선을 띄운다. 풍선이 떠 있는 동안 칸 아래 안내는 자리만 남기고 감춘다.
단이 가운데 정렬이라 안내를 빼서 높이가 바뀌면 위의 이웃집까지 움직이기 때문이다. 그림 자리에는 이웃집 창의 집 아이콘을 32px로 넣었다.
16칸 그림의 한 칸이 정수 픽셀이 되는 자리다(known-issues 67).

눌러 보기 점검 732개가 실패 0개, 밤 대비 점검이 실패 0개(로그인 화면의 글자 33개 포함)였다. 처음 온 사람(이웃집 여섯 집)과 내 집이 있는 사람의 화면을 1280×840으로 찍어,
두 줄 풍선까지 가운데 띠 안에 들고 왼쪽 단의 초기화 확인 글(링크와 아이디가 있을 때의 가장 긴 글)이 한 줄에 드는 것을 봤다.
