# 2026-11-26 관리자 도구: 방 주인의 계정에 비밀번호 넣기 (soomin007)

## 한 일
아이디와 비밀번호 로그인(F36)에서 사용자는 비밀번호를 스스로 되찾을 수 없다.
그래서 Admin이 방 주인의 계정에 비밀번호를 넣는 도구를 `tools/admin-password.mjs`로 만들었다.
비밀번호를 만들기 전에 브라우저 저장소가 비어 방을 고칠 수 없게 된 주인의 익명 계정에 비밀번호를 달 때와,
비밀번호를 잊은 주인에게 새 비밀번호를 넣을 때 쓴다. 같은 날 이 도구로 저장소가 비어 고칠 수 없던 방 하나를 되살렸다.

## 바꾼 파일
- `tools/admin-password.mjs`(새 파일): 관리자 도구. Google Cloud Shell에서 프로젝트 주인의 구글 계정으로 돌린다
- `tools/check.py`: `check_admin_password`. 도구가 따로 둔 이메일 꼴과 아이디 규칙이 `src/cloud.js`와 글자까지 같은지 본다
- `docs/file-map.md`, `docs/guide.md`, `docs/requirements.md`(F36), `docs/tasks.md`

## 정한 것과 이유
- 이 PC가 아니라 Cloud Shell에서 돌린다. 관리자 요청(Identity Toolkit의 `accounts:update`, 아이디 목록 읽기)에는 프로젝트 주인의 구글 계정 토큰이 들고,
  그 토큰을 PC로 옮기지 않으려는 것이다. 다른 파일을 부르지 않아 파일 하나만 올리면 된다. Firebase 웹 설정의 키는 배포된 사이트에서 읽는다.
- 사이트와 같은 이메일 꼴로 익명 계정에 이메일과 비밀번호를 단다. 계정 번호가 그대로라 방과 쪽지, 기록이 모두 이어진다.
  그 줄들은 사이트에서 글자 그대로 옮겨 두고 `check.py`가 견주게 했다. 달라지면 이 도구로 넣은 비밀번호로 로그인할 수 없다.
- 진짜 계정에 하기 전에 버릴 익명 계정으로 같은 일(비밀번호 달기, 새 비밀번호 넣기, 아이디 문서 만들기)을 해 보고 지운다.
  관리자 길로 익명 계정에 비밀번호를 다는 것을 미리 시험해 보지 못해서 넣었다.
- 로그인 아이디는 이 방의 주인이 만든 것이 있으면 그것을 쓰고, 없으면 묻는다. 이 방을 가리켜도 주인이 아닌 계정이 만든 아이디는
  사이트의 로그인에 쓰이지 않으므로 받지 않는다. 가짜 서버 시험에서 이런 아이디를 받아들여 비밀번호를 단 뒤에야 멈추는 결함을 찾아 고쳤다.
- 비밀번호는 명령줄 인자가 아니라 화면에 내지 않는 입력으로 받는다(인자는 셸 기록에 남는다). 화면과 파일 어디에도 적지 않는다.
- 도중에 멈추면 진짜 계정에 한 일(없음, 아이디만, 아이디와 비밀번호)을 알리고, 다시 돌리면 이어서 한다.

## 남은 일과 알아 둘 것
- 확인은 레포 밖의 가짜 서버(fetch와 gcloud를 바꿔 친 것)로 했다. 정상, 다시 돌리기, 아이디만 만든 뒤 이어 하기, 그만두기,
  잘못된 아이디와 비밀번호, 계정 없음, 다른 이메일, 사용 중지, 관리자 요청 거절을 돌렸다.
  요청을 하나씩 서버 오류와 연결 끊김으로 실패시킨 42가지에서 멈추는 곳과 시험 계정 뒷정리도 보았다.
- 실제 서버에서는 2026-11-26에 한 번 돌려 끝까지 됐다. 그 뒤 레포의 말투 표에 맞춰 터미널 말을 해라체로 바꾸고,
  이메일을 만드는 줄을 사이트와 글자까지 같게 바꿨다(만드는 주소는 같다). 차례는 그대로다.
- 주인은 로그인한 뒤 아이디와 비밀번호 창에서 비밀번호를 바꾼다. 아이디는 공유하기 창에서 지운 뒤 새로 정해 바꾼다.
- 터미널의 화면에 내지 않는 입력은 실제 Cloud Shell에서만 돌려 봤다. 이 PC의 시험은 파이프 입력이다.
